## 18.1 POSIX 强一致性法则与分布式缓存的冲突

POSIX 标准对本地文件系统的读写语义有着极其刚性的法律级定义：
> *“当一个进程对文件某一范围的 `write()` 调用返回后，任何进程对同一范围发起的后续 `read()` 调用，必须能够立即观察到刚刚写入的数据。”*

在单机系统中，由于所有进程共享同一份物理内存与全局 PageCache，这一保证是天然成立的。
但在分布式网络中，这引发了巨大的工程对抗：

```text
+-------------------------------------------------------------------------------+
|                       分布式环境下的缓存一致性冲突                            |
+-------------------------------------------------------------------------------+

计算节点 A (Client A)                                 计算节点 B (Client B)
  |                                                           |
[在本地 PageCache 写入 4KB]                                   |
[未同步下刷到远端 OST]                                        |
  |                                                           |
  +--- (POSIX 刚性要求: 节点 B 必须立即读到该 4KB 数据!) -------> |
                                                              |
                                                    [在本地发起 read()]
                                                    如果不加控制，节点 B 读到了
                                                    自己的旧本地缓存或 OST 上的旧数据!
                                                    => 发生致命的“数据穿越与脏读”!
```

### 18.1.1 破局之钥：锁与缓存强绑定

Lustre 破解该矛盾的核心铁律是：**“缓存即锁，失锁即失缓存”**。
- 客户端在本地内存缓存某个文件的特定 Extent 数据的前提，是**必须持有覆盖该区间的 LDLM 读锁（PR）或写锁（PW）**；
- 一旦任何其他节点试图修改该区间，服务端会向当前持锁客户端发送 **Blocking AST**；
- 客户端在收到 Blocking AST 后，必须在规定时间内将内存中的脏页强制推向 OST，并**主动将本地对应的 PageCache 全部作废（Invalidate）**；
- 唯有在持锁客户端确认完成下刷与作废后，服务端才会将锁授予新节点。强一致性由此无懈可击地达成！

## 18.2 写后读（Read-After-Write）跨节点执行时序

```text
+-------------------------------------------------------------------------------+
|                       写后读强一致性跨节点流转全景                            |
+-------------------------------------------------------------------------------+

Client A (写入者)                   OST (服务端)                  Client B (读取者)
   |                                     |                               |
[持有 [0, 4M] PW 写锁]                  |                               |
[在本地 PageCache 异步写 4MB]            |                               |
   |                                     |                               |
   |                                     |<--- (1) 发起 read([0, 4M]) ---|
   |                                     |     (申请 PR 读锁)            |
   |                                     |                               |
   |<-- (2) Blocking AST 阻断回调 -------|     [发现锁冲突，挂起 Client B]
   |    (请立即下刷脏页并降级锁!)        |                               |
[触发 osc_cache_writeback_range()]       |                               |
[通过 Bulk RDMA 将 4MB 脏页倾泻落盘]     |                               |
[本地 Page 标记由 Dirty 转为 Clean]      |                               |
[将本地锁降级为 PR 读锁]                 |                               |
   |                                     |                               |
   |--- (3) Cancel / Downgrade 确认 ---->|                               |
                                         |                               |
                                         |--- (4) 授予 PR 读锁 --------->|
                                         |    (Completion AST 唤醒)      |
                                         |                               |
                                         |<--- (5) RDMA Read 拉取数据 ---|
                                         |                               |
                                         | [读到 Client A 写入的绝对最新数据!]
```

通过这一套严密的网络协作，Lustre 在完全不牺牲异步客户端写入性能的前提下，从物理机制上彻底杜绝了并发脏读。

## 18.3 分布式内存映射（`mmap`）的实现内幕

在现代大数据分析、数据库与深度学习数据加载器（如 PyTorch DataLoader）中，`mmap` 被广泛用于实现零系统调用开销的内存直读。
但在分布式文件系统上实现 `mmap` 是内核工程界的珠穆朗玛峰：
**进程通过指针直接访问虚拟地址，根本不经过 `vfs_read()` 或 `vfs_write()`，文件系统如何捕获读写动作并申请分布式锁？**

### 18.3.1 缺页异常与锁驱动：`ll_fault()`

Lustre 在 [`lustre/llite/file.c`](https://github.com/lustre/lustre-release/blob/master/lustre/llite/file.c) 中深度重载了 Linux 虚拟内存的 `struct vm_operations_struct`：

```c
static const struct vm_operations_struct ll_file_vm_ops = {
	.fault		= ll_fault,		/* 处理缺页异常 */
	.page_mkwrite	= ll_page_mkwrite,	/* 只读页转为可写脏页 */
};
```

```text
+-------------------------------------------------------------------------------+
|                       分布式 mmap 缺页与锁申请时序                            |
+-------------------------------------------------------------------------------+

用户态执行: char c = *(ptr + 4096);  (触发 CPU 缺页中断 MMU Page Fault!)
                         |
                         v
1. Linux 内核 VM 层捕获异常: handle_mm_fault()
                         |
                         v
2. 调用 ll_fault() [lustre/llite/file.c]:
   - 构造 CIT_FAULT 类型的 cl_io 上下文!
   - 跨网络向 OST 申请覆盖该页面的 LDLM EXTENT 读锁 (PR Mode)!
   - 发起底层 Bulk RDMA 将该 4KB 页面从远端 OST 读入物理内存
   - 建立进程虚拟页表（PTE）映射
                         |
                         v
3. CPU 恢复执行，指针读取成功!

用户态执行写操作: *(ptr + 4096) = 'A'; (只读页面首次触发写入!)
                         |
                         v
4. 调用 ll_page_mkwrite():
   - 检查当前持有的锁是否支持写入?
   - 若当前仅持有 PR 读锁，立即触发锁升级: 向 OST 申请 PW 范围写锁!
   - 预留 Grant 信用额度，将页面标记为 Dirty!
```

通过将 CPU 硬件缺页中断与远端 LDLM 锁机制熔铸在一起，Lustre 让分布式文件系统具备了单机内存映射的全部平滑能力。

## 18.4 AI 时代的性能核武：PCC（Persistent Client Cache）

在超万卡大模型预训练中，通常会遇到一个极致的物理挑战：
- 几千个计算节点在每个 Epoch 开始时，都需要并发读取同一个 500GB 的 Tokenized 数据集；
- 几千台机器同时跨 InfiniBand 网络拉取这 500GB 数据，累计瞬间网络流量高达 **500TB**！存储集群的网卡与 OST 瞬间被打爆瘫痪。

为此，Lustre 研发了 **PCC（Persistent Client Cache，持久化客户端缓存）**（[`lustre/llite/pcc.c`](https://github.com/lustre/lustre-release/blob/master/lustre/llite/pcc.c)）：
**“利用每台计算节点自带的超高速本地 NVMe SSD，将热点共享数据直接下沉持久化在本地文件系统（如 ext4/xfs）中！”**

```text
+-------------------------------------------------------------------------------+
|                       PCC 客户端本地持久化缓存架构全景                        |
+-------------------------------------------------------------------------------+

+-------------------------------------------------------------------------------+
| 计算节点 (Compute Node)                                                       |
|                                                                               |
|  [用户访问 /mnt/lustre/datasets/llama3.bin]                                   |
|                          |                                                    |
|                          v                                                    |
|  +-----------------------------------------------+                            |
|  | PCC 拦截路由引擎 (pcc.c)                       |                            |
|  +-----------------------+-----------------------+                            |
|                          |                                                    |
|           +--------------+--------------+                                     |
|           | (未命中 / 首次加载)         | (已命中缓存!)                       |
|           v                             v                                     |
|    从远端 OST 阵列拉取           直接重定向至宿主机本地 NVMe 盘:       |
|    并静默存入本地 NVMe 盘        open("/mnt/local_nvme/pcc/llama3.bin")       |
|                                         |                                     |
|                                         v                                     |
|                              读吞吐飙升至 7GB/s! 零网络流量! 零后端压力!       |
+-------------------------------------------------------------------------------+
```

### 18.4.1 PCC 双模态运作

1. **PCC-RO（只读多节点共享模式）**：
   专为 AI 训练集设计。数千个节点并发将只读数据拉入本地 NVMe 盘并锁定。后续的训练轮次（Epochs）**100% 走本地 NVMe 盘读取，全网网络流量直接归零！**
2. **PCC-RW（独占读写模式）**：
   将特定的临时目录（如编译中间件或单机临时 Checkpoint）绑定至本地 NVMe。写入完全在本地极速落盘，后台通过 HSM 机制异步自动回填同步到中央 Lustre。

## 18.5 生产实战：多节点并发追加写“锁颠簸（Ping-Pong）”事故

### 18.5.1 现场故障复盘：1000 进程写日志拖垮全机房

某气象模拟作业启动了 1,024 个并行 MPI 进程。代码中每个进程每秒钟都会向同一个中央日志文件 `/mnt/lustre/shared.log` 执行一次追加写入：
`fprintf(fp, "Worker %d finished step %d\n", rank, step); fflush(fp);`
随后，所有的计算节点 GPU 处于完全饥饿状态，系统监控显示该日志文件的写 IOPS 暴跌到**每秒不到 50 次**，MDT 和 OST 陷入疯狂的锁震荡报警。

### 18.5.2 根因剖析：锁乒乓（Lock Ping-Pong Effect）

```text
+-------------------------------------------------------------------------------+
|                       致命的锁乒乓 (Lock Ping-Pong) 震荡效应                  |
+-------------------------------------------------------------------------------+

Node 0: 申请写锁 [EOF, EOF] -> 获得锁 -> 写 100 字节 -> 发送网络 RPC
  ^
  | (此时 Node 1 也要追加写入!)
## 18.5 真实生产事故复盘：千节点并发追加写同一个共享日志触发“锁乒乓”雪崩

### 18.5.1 事故现场：万卡集群 IOPS 彻底归零
某国家级实验室在 1,024 台计算节点上启动了一个大规模天气预报集合计算。
作业启动后，集群整体 IO 吞吐从平时的 80GB/s 暴跌到不足 20MB/s！所有节点的 CPU利用率接近 0%，但都在无休止地等待存储返回，`top` 显示几千个进程全部停在 `D` 状态。
服务端 MDS 与 OST 监控显示：网络数据包极少，但 LDLM 锁撤销消息（Blocking AST）呈现每秒数万次的恐怖尖刺！

### 18.5.2 根因定位与抢救分析
1. **代码走查发现致命反模式**：
   工程师审查用户提交的 Fortran/C 源码，发现所有 1,024 个并行进程在每一轮迭代结束时，都会执行同一行代码：
   ```c
   /* 致命反模式: 几千个并发进程同时向根目录同一个文件追加写心跳 */
   FILE *fp = fopen("/mnt/lustre/run.log", "a");
   fprintf(fp, "Rank %d completed step %d\n", my_rank, step);
   fclose(fp);
   ```text
2. **锁乒乓（Lock Thrashing）物理过程**：
   - 每次调用以追加方式写入时，客户端必须向服务端申请该文件末尾的排他写锁（Exclusive Lock, `LCK_PW`）；
   - Node 0 刚申请到写锁并缓存在本地，Node 1 立即发来冲突的写锁申请；
   - OST 只能向 Node 0 发送 Blocking AST 强制其刷盘并释放锁；
   - 紧接着 Node 2 又发来申请，OST 又把锁从 Node 1 剥夺走；
   - 整个集群 99.9% 的宝贵网络带宽和 CPU 时间，全部消耗在“发 Blocking AST -> 刷盘 -> 释放锁”的恶性死循环中！

### 18.5.3 架构加固与生产处方

```bash
# 方案 1: 使用 Lustre 组锁 (Group Lock)
# 允许同一作业的所有进程共享同一个写锁上下文，完全消除相互撤销!
# 应用程序通过 ioctl(LL_IOC_GROUP_LOCK, gid) 获取组锁

# 方案 2: 使用 lfs flock 针对性优化 (或在挂载时使用 localflock)
mount -t lustre -o localflock 192.168.10.1@tcp:/lustre /mnt/lustre

# 方案 3 (软件架构黄金解): 消除共享日志文件反模式
# 严禁数千进程直接写同一个小文本!
# 强制改造为: 每个 rank 写独立文件 (如 log.rank_0, log.rank_1)
```text

## 18.6 分布式缓存与并发访问调优 Checklist

在维护多进程并发读写、分布式 mmap 与 PCC 本地缓存时，必须落实以下规范：

- [ ] **严禁多节点并发无锁追加写单文件**：
  严禁跨网络成百上千进程并发向单个普通文件执行高频 `write(..., "a")`。必须拆分为分进程独立文件或采用 MPI-IO 结合 `Group Lock`。
- [ ] **分布式 mmap 性能与跨节点同步核查**：
  若应用程序依赖 `mmap()` 共享读写，确认上层应用已正确调用 `msync()`，且了解分布式内存映射下由于伪共享（False Sharing）引发的频繁页面失效开销。
- [ ] **PCC（Persistent Client Cache）热数据自动下沉**：
  在 AI 训练与模型推理节点上，推荐配置 PCC 规则（`/etc/lustre/pcc.conf`），将训练读取的高频小图片、Tokenizer 词表和特征向量自动缓存至本地 NVMe SSD，实现只读命中完全不消耗存储网络带宽。
- [ ] **本地文件锁标志位（localflock）审慎评估**：
  若用户明确不需要跨节点文件锁强一致性，在计算节点挂载时添加 `-o localflock`，可将 `flock()` 限制在单机内存中，避免频繁向 MDS 发送锁网络交互。
